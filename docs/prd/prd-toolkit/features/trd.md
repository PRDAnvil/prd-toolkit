# TRD

`prd trd <prd_dir>` prints the PRD's technical view: one Markdown document that sets what the PRD says about
how the system is built (its stack, its architecture, its standards and skills registries, its contract types)
beside what the repository holds (each area's files and requirements, each requirement's `Source:` line, and the
files no area covers). The view is an output, never a part of the PRD: nobody edits it, no gate approves it, no
check reads it, and the black-box tester never reads it. It is made again whenever it is wanted, for a release
say, and the same commit and the same PRD folder always give the same bytes, so two views diff cleanly. Its use
is to learn which of its parts people want to keep by hand: such a part becomes a managed document only by a
later change to this PRD, and anything the black-box tester needs stays in the PRD whatever that change
decides. Its modules are `prd-toolkit/scripts/prd_trd.py` and `prd-toolkit/scripts/prdlint/trd.py`; the
launcher runs it as `prd trd` (hooks-install AC-119.1), and install vendors `prd_trd.py` into `.prd-toolkit/`
(AC-098.1), so a target repository runs it as `.prd-toolkit/prd trd`. A slash command, an HTML page, a record of design
decisions and any check of what the view says are out of scope.

Words used below.

- The **repository** is the git work tree that holds the PRD folder, and **HEAD** the commit that
  `git rev-parse HEAD` names there; `<sha7>` is the first 7 characters of HEAD's full name.
- The **files at HEAD** are the paths `git ls-tree -r --name-only HEAD` prints, relative to the repository's
  root: files in the working tree that HEAD does not hold are not among them.
- `<folder>` is the PRD folder's path relative to the repository's root, written with `/` (`docs/prd/orders`).
- A section's **body** in `prd.md` is its lines after its `## ` heading, up to the next line that starts with
  `## ` or the end of the file, with the empty lines at its start and at its end removed.
- A path **matches** a Boundary glob, a backticked span of an adoption-map Boundary cell, when the glob holds no
  `*` and equals the path; when the glob ends in `/**` and the path starts with the text before the `**`; or
  when the glob holds `*` and no `**` and the path, split at `/`, has as many parts as the glob, each part
  matching its glob part, where a `*` stands for any run of characters, none included.
- A block's **status word** is the first word of its `Status:` value, so `live (since 1.0.0)` is `live`.

### FR-265 Print the technical view
Status: approved
Flow: 1. find the repository and HEAD → 2. read the PRD folder → 3. build the header and the eight sections →
      4. print them, or write them to the `--out` file
Acceptance (EARS):
- AC-265.1 When `prd_trd.py <prd_dir>` is run on a PRD folder in a repository that has a commit, the trd
  command shall print to stdout the line `# Technical view: <prd> <version>` (`<prd>` and `<version>` the
  `prd:` and `version:` values of `prd.md`'s frontmatter), an empty line, and the line
  ``Generated by prd trd from `<folder>` at <sha7>. Do not edit it: run prd trd again. The PRD is the authority, and the black-box tester never reads this file.``;
  then, for each of the sections Stack, Architecture, Components, Requirements to code, Standards, Skills,
  Contracts and Uncovered code, in that order, an empty line, the line `## <section>`, an empty line, the
  section's `From:` line, an empty line and the section's body; shall end stdout with the newline of the last
  body line, and no empty line after it; and shall exit 0.
- AC-265.2 The trd command shall write as the bodies of Stack, Architecture, Standards and Skills the bodies of
  `prd.md` sections 1, 4, 5 and 6, line for line, after the `From:` lines `From: prd.md section 1.`,
  `From: prd.md section 4.`, `From: prd.md section 5.` and `From: prd.md section 6.`.
- AC-265.3 The trd command shall write as the `From:` line of Contracts `From: prd.md section 7.`, and as its
  body the line `These stay in the PRD: the black-box tester writes its tests from them.`, an empty line, the
  line `| Type | Files (glob) |`, the line `|---|---|` and one line `| <type> | <files> |` per row of the
  section 7 table, in the table's order, `<type>` and `<files>` being that row's Type and Files (glob) cells as
  the row holds them, with the white space around each removed.
- AC-265.4 When the trd command is run twice on the same HEAD, with no file of the PRD folder changed between
  the two runs, it shall print the same bytes both times; and the view shall hold no date or time.
- AC-265.5 When `prd_trd.py <prd_dir> --out <file>` is run, and `--out` is not refused (AC-267.1), the trd
  command shall write to `<file>` the bytes it prints to stdout without `--out`, in place of any text the file
  held, creating the file but not its folder; shall print the one stdout line `wrote <file>`, `<file>` as the
  argument gives it; and shall exit 0.
Errors: -
Edge cases: a PRD that lint refuses is read as the loader reads it, since the view checks nothing → AC-265.1; a
section body that is `Not applicable: <reason>` is written as it is → AC-265.2; the PRD folder's files are read
from the working tree, so an uncommitted edit to `prd.md` shows in the view while the header still names HEAD →
AC-265.1; a `--out` file in the repository but outside the PRD folder is allowed, and the view does not change
when it is committed, since it is no part of the PRD folder → AC-265.4, AC-265.5
Tests: T-265.1 [integration], T-265.2 [integration], T-265.3 [integration], T-265.4 [integration], T-265.5 [integration]  (test-cases/trd.yaml)

### FR-266 Map the areas and the requirements to the code
Status: approved
Flow: 1. read the adoption map, the features files and each block's `Source:` line → 2. list the files at HEAD →
      3. count each area's files, check each `Source:` path and list the files no area covers
Acceptance (EARS):
- AC-266.1 When the PRD folder holds `adoption.md`, the trd command shall write as the `From:` line of
  Components `From: adoption.md and the files at <sha7>.`, and as its body the line
  `| Area | State | Boundary | Files | Requirements |`, the line `|---|---|---|---|---|` and one line per row of
  the adoption map, in the map's order, whose Area, State and Boundary cells are that row's, with the white space
  around each removed; whose Files cell is the number of files at HEAD that match one or more of the row's
  Boundary globs; and whose Requirements cell lists each UJ, FR and NFR block of `features/<area>.md`, in the
  file's order, as `<ID> <status word>`, joined by `, `, or is `-` when that file does not exist or holds no
  block.
- AC-266.2 When the PRD folder holds no `adoption.md`, the trd command shall write as the `From:` line of
  Components `From: the features files and the files at <sha7>.`, and as its body the two lines AC-266.1 names
  first and one line per `features/*.md` file, in the order of the file names, whose Area cell is the file's name
  without `.md`, whose State, Boundary and Files cells are each `-`, and whose Requirements cell is as AC-266.1
  says.
- AC-266.3 The trd command shall write as the `From:` line of Requirements to code
  `From: the Source: lines of the requirement blocks, checked at <sha7>.`, and as its body the line
  `| ID | Status | Source | At HEAD |`, the line `|---|---|---|---|` and one line
  `| <ID> | <status word> | <source> | <at HEAD> |` per UJ, FR and NFR block that has a `Source:` line, in the
  order of the `features/*.md` file names and then `nfr.md`, each file's blocks in its order, `<source>` being
  the block's `Source:` value with the white space around it removed and each continuation line joined to it by
  one space, and `<at HEAD>` being `yes` when the text before the value's first `:` is a file at HEAD whose text
  at HEAD has at least as many lines as the number after that `:`, else `no`; and when no block has a `Source:`
  line, the one line `No requirement block has a Source: line.` as the body.
- AC-266.4 When the PRD folder holds `adoption.md`, the trd command shall write as the `From:` line of Uncovered
  code `From: the files at <sha7> that no Boundary glob of adoption.md matches.`, and as its body one line
  ``- `<path>` `` per file at HEAD that lies outside `<folder>/` and outside `.prd-toolkit/` and that no Boundary
  glob of any row matches, whatever the row's state, in Python's string order; or, when there is no such file,
  the one line `Every file is in an area's Boundary.`; and when the folder holds no `adoption.md`, the `From:`
  line `From: prd.md section 8.` and the one body line
  `No adoption map: every path outside the PRD folder and .prd-toolkit/ is covered.`
Errors: -
Edge cases: a Boundary glob that matches no file counts 0 → AC-266.1; a file that two rows' globs match counts in
both rows and is not uncovered → AC-266.1, AC-266.4; a file in the working tree that HEAD does not hold is not
counted, listed or checked → AC-266.1, AC-266.3, AC-266.4; a path that only starts with `.prd-toolkit`, such as
`.prd-toolkit-notes.md`, is not inside `.prd-toolkit/` → AC-266.4; a `Source:` line whose number is past the
file's last line is `no`, as is one whose path HEAD does not hold → AC-266.3
Tests: T-266.1 [integration], T-266.2 [integration], T-266.3 [integration], T-266.4 [integration]  (test-cases/trd.yaml)

### FR-267 Keep the view out of the PRD
Status: approved
Flow: 1. check the PRD folder and the repository → 2. check the `--out` path → 3. print or write the view,
      changing nothing else
Acceptance (EARS):
- AC-267.1 If the `--out` path, resolved with its symbolic links followed, is the PRD folder, lies inside it, is
  the folder `.prd-toolkit` at the repository's root or lies inside that folder, the trd command shall print the
  one stderr line `refused: --out must lie outside the PRD folder and .prd-toolkit/`, print nothing on stdout,
  write no file and exit 1.
- AC-267.2 If `<prd_dir>` holds no file `prd.md`, the trd command shall print the one stderr line
  `prd_trd: <resolved folder>: no prd.md`; else if the folder lies in no git work tree, the one stderr line
  `prd_trd: <resolved folder> is not in a git work tree`; else if the repository has no commit, the one stderr
  line `prd_trd: the repository has no commit`; else if the `--out` file cannot be written (its folder does not
  exist, say), the one stderr line `prd_trd: cannot write <file>: <reason>`, `<file>` as the argument gives it
  and `<reason>` the operating system's message; `<resolved folder>` being `<prd_dir>` as an absolute path with
  its symbolic links followed; and in each case it shall print nothing on stdout, write no file and exit 2.
- AC-267.3 The trd command shall leave every file of the PRD folder and of `.prd-toolkit/` byte for byte as it
  was, and the output of `git status --porcelain` in the repository as it was, but for the `--out` file it
  writes.
Errors: -
Edge cases: an `--out` path that reaches the PRD folder through a symbolic link is refused → AC-267.1; an `--out`
path whose folder does not exist is not created: the command fails and writes nothing → AC-265.5, AC-267.2; a `<prd_dir>`
that does not exist holds no `prd.md` → AC-267.2; the git hooks and CI never run `prd trd`, since nothing
checks the view → AC-267.3
Tests: T-267.1 [integration], T-267.2 [integration], T-267.3 [integration]  (test-cases/trd.yaml)
Traces: cli:prd_trd
