# Testing

## Levels

| Level | Harness command | Environment | Gate | One test |
|---|---|---|---|---|
| unit | `uv run --directory prd-toolkit pytest -q -n auto tests --ignore tests/prd` | local | build | `uv run --project prd-toolkit pytest -q -n auto` |
| integration | `uv run --directory prd-toolkit pytest -q -n auto tests/prd` | local | build | `uv run --project prd-toolkit pytest -q -n auto` |

## Harness

- **Lifecycle.** Nothing runs between tests: there is no service or database. A test runs a CLI script as a subprocess with the test's own interpreter, `python <repo>/prd-toolkit/scripts/<script>` (not `uv run --script`, whose own stderr lines would break the stderr assertions), or calls the script's library, in a fresh temporary directory it creates itself.
- **Environment switch.** Not applicable: one environment, `local`; no test touches `production` (the marketplace).
- **Database access.** Not applicable: no database.
- **Tools on the runner.** python3 3.11 or later, uv and git on PATH, on macOS or Linux, whose file systems let a test create a symbolic link with `os.symlink`; the tests directory is `prd-toolkit/tests/`; the Levels commands run pytest in the environment of `prd-toolkit/pyproject.toml`, which holds pyyaml, sqlglot, openapi-spec-validator and markdown-it-py, so a test may import `yaml`. The first run in a worktree, with an empty test cache (Clean state), needs network access to the package index for the uv scripts' dependencies; later runs reuse the cached packages. The eval-scaffolds cases also need bash on PATH (T-073.4), and T-073.1 to T-073.3 each run `uv lock` and `uv sync` for the scaffold repository, so they need network access to the package index on every run. T-019.2 needs that access on every run: its inner session starts from an empty test cache of its own.
- **Clean state.** Every test starts from its own pytest `tmp_path`; a PRD folder or git repository it needs is copied or built there, and nothing is shared between tests. The uv cache is the one exception (NFR-019): the session points `UV_CACHE_DIR` at its test cache, the folder `PRD_TEST_UV_CACHE` names (a relative path resolved against the working directory pytest starts in) or `prd-toolkit/.uv-test-cache/` (git-ignored) when it is unset or empty, before any test runs, so every uv command a test starts, a git hook's included, uses it. When the whole run ends, once and never while a pytest-xdist worker still runs, the session deletes the test cache's `environments-v2` folder and keeps its downloaded packages.
- **Subprocess environment.** A script runs with the runner's environment, which is the test process's environment when the command starts (so it holds the session's `UV_CACHE_DIR`, Clean state), minus `PYTHONIOENCODING`, `PYTHONPATH` and `PYTHONHOME`, which would hide the locale or reach a bare virtual environment, and minus `PRD_LINT_CI`, which would skip checks a case expects, and minus `PRD_HELP_FILE`, which would point the help command at another catalogue, plus the case's own `env`. A run written as a mapping `{env: …, command: …}` adds that `env` for that run only, and a `cwd:` in such a mapping is that run's working directory in place of the case's `cwd`.
- **In-process calls.** A case's `call:` runs the named function inside the test process instead of a subprocess, with the same environment rules (set through pytest's monkeypatch), and `return` is the value it returns; its stdout and stderr are captured.
- **Persistent environments.** Not applicable: no environment keeps data.
- **Layout.** Unit tests are `prd-toolkit/tests/test_*.py`, written by the builder; the black-box characterization tests are `prd-toolkit/tests/prd/test_<area>_*.py`, with a hyphen in the area's name written as an underscore (`test_lint_cli_*.py`), with the area's shared helper beside them as `<area>_support.py` (`lint_cli_support.py`); a test of an NFR block in `nfr.md`, which belongs to no area, takes `nfr` in the area's place (`test_nfr_*.py`, `nfr_support.py`); each citing its T-id in its docstring as `@prd T-nnn.n`. Trace counts every `@prd T-nnn.n` in a file under the test roots as a citation, so a test that must hold such a text for another PRD's test case (a fixture's line, an expected finding) builds it from parts (`"@" + "prd"`) and never writes it whole. Test roots: `prd-toolkit/tests/`
- **HTTP requests.** Not applicable: no HTTP API.
- **Fixtures.** A fixture is a PRD folder (or a file of one) under `contracts/fixtures/<name>/`, or the one named `repo/vendored`, this repository's committed vendored copy (the Fixtures table), which a case names in its setup, not in `preconditions:` (that list holds `contracts/fixtures/` names only); a test copies it into its `tmp_path` before running the script on it. A fixture may also be a scratch repository (`status-next/base`, `status-next/empty`, `practices/repo`): one YAML file whose keys are paths from the repository root, the PRD folder's files and a test file beside it, which the Setup steps write and put under git. Load paths are relative to this PRD folder's `contracts/fixtures/`, which a test reaches as `<repo>/docs/prd/prd-toolkit/contracts/fixtures/` (`<repo>` is the repository root).
- **Browser identity.** Not applicable: no UI.
- **Assertions.** A case's `expect.output` gives the exit code and the output lines it asserts; output lines a case does not list are not asserted unless the case says the output is exact. A case's `expect.errors` lists codes of `contracts/errors.yaml`, which holds none, since every script reports a failure as an exit code and a stderr line; so `errors: []` asserts nothing, and what a case asserts of stderr only its `expect.output` keys (`stderr` and the `stderr_*` keys) and its `symptom:` say. `stdout_exact` and `stdout` compare the whole stdout byte for byte: a test captures a command's stdout and stderr as bytes, never in text mode (whose newline translation turns a `\r` into `\n`), and compares them with the expected text encoded as UTF-8; `stdout_exact_lines` compares its list of lines (`str.splitlines()`) to the list, in order and with nothing else; `stdout_lines_any_order_exact` compares the same lines in any order; `stdout_lines_in_this_relative_order` finds each listed line, whole, after the one before it, with other lines allowed between; `stdout_first_line` is the first of those lines; `stdout_contains_line` finds one whole line; `stdout_contains` finds a substring, or each string of a list. `stdout_not_contains` is the stdout twin of `stderr_not_contains`: a substring, or each string of a list, that stdout must not hold anywhere; `stdout_count_of_line` is a mapping `{line, count}`, and the number of stdout lines (`str.splitlines()`) equal to `line` must be `count`. `stderr` compares the whole stderr byte for byte, and each `stderr_*` key works as its `stdout_*` twin (`stderr_first_line_starts`, `stderr_last_line` and `stderr_single_line_starts` on its lines, `stderr_not_contains` as a substring that must be absent). `stderr_first_line_starts` requires the first stderr line (`str.splitlines()`) to start with the text, and `stderr_single_line_starts` requires stderr to hold exactly one line, which starts with the text. A case with `runs:` runs each listed command on its own; `each_run` holds for every run, and `run_1`, `run_2`, … for the run at that position. A finding line compares exactly, as `<file>:<line>: <rule>: <message>`. `stdout_json` requires the whole stdout to be one line ending in a newline, parses that line as one JSON object and compares it to the case's mapping, every key and value, a YAML scalar compared as the JSON value it reads as (`1.0.0` a string, `1` a number, `[]` an empty list); `stdout_json_first_keys` lists the object's first keys, in order. `stdout_json_at` also requires the whole stdout to be one such line, and is a mapping from a path to a value: a path is object keys and list indexes joined by `.` (`entries.0.key`, `rules.ac-ears.severity`), the value at each path must equal the mapping's, and nothing else in the document is compared; `stdout_json_keys_at` maps a path (`""` for the document itself) to the exact list of the keys of the object at that path, in order, with the same one-line requirement on the whole stdout. `relations` is a list of statements in plain words, each relating the outputs of the case's runs to each other (`run_1`, `run_2`, … by position); the test asserts each statement as written, and "stdout lines" in a statement are `str.splitlines()` of that run's stdout. `next_part_lines` compares the Next part of a status report: the stdout lines (`str.splitlines()`) from the first line up to, and not including, the first line that is `## Header`, which the stdout must hold, are compared to the list, in order and with nothing else. `next_items_json` requires the whole stdout to be one line ending in a newline, parses that line as one JSON object, and compares the entries of its `items` whose `part` is `Next`, in order, to the case's list of mappings, every key and value as `stdout_json` compares them; those entries must also come before every other entry of `items`. `pack_part_titles` compares the stdout lines (`str.splitlines()`) that start with `## ` (two number signs and a space, so no `### ` line is among them), in order, to the list, with nothing else. `pack_part_lines` maps a part's title to a list of lines: the stdout lines from the line `## <title>`, which the stdout must hold exactly once, up to, not including, the next line that starts with `## `, or to the end of stdout, are compared to the list, in order and with nothing else. `<today>` in an expected value is the date a command writes as today, `YYYY-MM-DD`: the local date of the machine the run is on, as Python's `datetime.date.today()` gives it, which `prd change record` and `prd change pack` take for `updated:` and the section 14 row, and `prd error new` for `Detected:`; the test takes that date just before and just after the command runs and accepts either, since a run that crosses midnight may write either day.
- **Waits.** Every command runs to completion before the test asserts, but in T-079.4 (`test-cases/error-replay.yaml`), which starts `prd error replay` in the background, waits up to 30 seconds for the file its runner writes, sends the command SIGINT and waits up to 30 seconds for it to end; and in T-254.6 (`test-cases/inbox-cards.yaml`), which starts `prd gates wait` in the background, waits up to 30 seconds for its waiting marker, answers the gate and waits up to 30 seconds for `wait` to end; a wait that runs out fails the test.
- **Effects.** A file a command writes is compared by content; "unchanged" means byte-identical to before the command ran.
- **Leaks.** Not applicable: no classified data.
- **Acceptance.** Not applicable: no acceptance level.

## Setup steps

The status-next cases (`test-cases/status-next.yaml`) build their state with these steps, which a case names in its `setup:` and the test runs in that order. The steps' own git commands and every run of a status-next case use the Subprocess environment (Harness) minus `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and `GIT_COMMON_DIR` as well, so a suite started from a git hook reads the scratch repository and never the outer one. `<tmp>` is the root of the scratch repository, and a relative path below is inside its PRD folder, `<tmp>/docs/prd/orders`. `files.<key>` is the text at that key of fixture status-next/files. A step that writes a file creates its parent folders and writes the text byte for byte, as UTF-8. Where the toolkit keeps what the steps write: a deploy run log is `<git common dir>/prd-toolkit/deploys/<run id>.jsonl`, which for the repository that `git init` makes in `<tmp>` is `<tmp>/.git/prd-toolkit/deploys/<run id>.jsonl`; the answers file of an area being adopted is `<repository root>/.prd-confirm-<area>.json`.

The hooks-install cases (`test-cases/hooks-install.yaml`) build their state with step N0E and the names their file's header defines (`VENDOR`, `DEPLOY`, `SHIM`, `LINE`, `GH`, `GL`). `<tmp>` is the test's tmp_path; "N0E in `<tmp>/a`" builds the scratch repository in that folder. A step's commands run with the scratch repository's root as the working directory and must exit 0; a step whose command exits other than 0, or that does not find the line or the text it is to change, ends the test as an error, not a failure, since the state the case needs was never built. The steps' own git commands, a test's own git commands (those a case's `effects` read) and every run of a hooks-install case use the Subprocess environment (Harness) minus `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and `GIT_COMMON_DIR`, plus `GIT_CONFIG_GLOBAL=<tmp>/gitconfig-empty`, an empty file the test writes before its first step, or before its first run when the case names no step, and `GIT_CONFIG_NOSYSTEM=1`; `PRD_PLUGINS_FILE`, `STUB_LOG` and `STUB_EXIT` are removed from that environment as well, so the toolkit reads the runner's own installed-plugins file and a stub launcher sees only what its case sets; a case's own `env` is added for the case's runs only and reaches no step. A check that a step names ("check that … exits other than 0") is not one of the commands that must exit 0: when the check does not hold, the test ends as an error. The test sets `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM` so in its own process, through pytest's monkeypatch, before its first step, so that the `git init` of the borrowed step N0E inherits them too: for these two variables this paragraph overrides the rule of Borrowed steps and helpers that a borrowed step keeps its own area's environment. Every line a step writes, the last one included, ends in a newline, unless the step says the file has no newline at its end, and a step that appends a line to a file whose last line has no newline ends that line first. Where a case compares the files under a folder, with another folder or with the folder as it was before a run ("unchanged"), the comparison is of the whole set of relative paths and of each file's bytes, so an added or a removed file is a difference; the files inside a `__pycache__` folder and the files ending `.pyc` are left out of it, since a run of a script in that folder may write them. A file that a step or a run of a case writes for git or `sh` to run (a hook file, `hook.sh`, a stub launcher) gets mode 0o755. A relative path in a step is relative to the scratch repository's root, never to the PRD folder. An `effects` entry that is a mapping names a `file` and one form: `lines` compares `str.splitlines()` of the file's text to the list, and the text must end in exactly one newline; `first_lines` compares the file's first lines to the list, as many as the list holds; `contains_lines_in_this_order` finds each listed line, whole, after the one before it, with other lines allowed between; `line_after` maps a line to the line that must directly follow the first line equal to it; `read_as_yaml` parses the file as YAML and maps a path (object keys and list indexes joined by `.`) to the value at that path, a key written `<path> keys, in order` to the list of the keys of the mapping at that path, and a key written `<path> length` to the length of the list at that path.
